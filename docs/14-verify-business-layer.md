# 14 · verify 的业务层视角

> **本文记录一个设计约束** —— 它比功能本身更重要。
>
> 对应实现：`src/cli/cmd_verify.cc`；测试：`tests/integration/test_verify_business.cc`（5 用例）。

---

## 一、要解决的问题

**现在的 verify 会说谎。**

它只看 DDS 层。业务收到 1000 条但内部失败 50 条时：

```
verify → events=1000, has_integrity_issue=false    ✓「数据完整」
实际   → 业务只处理成功 950 条                      ✗ 业务挂了 5%
```

"完整"这个结论在骗人。用户以为数据可用，拿去复盘，发现业务对不上，却不知道该怪谁。

---

## 二、★ 但这里有一条不能越过的边界

**verify 的职责是「数据完整性」，不是「业务正确性」。**

它不知道业务逻辑，也不该假装知道。所以：

| | 可以做的 | 不能做的 |
|---|---|---|
| 呈现 | 把 DDS 层与业务层的数字**分开列出** | 判断"业务处理得好不好" |
| 结论 | DDS 层有没有缺口、有没有丢数据 | 业务失败 50 条是不是问题 |

**为什么"业务失败 50 条"不能算问题**：那 50 条可能完全是正常的 ——
50 个订单被用户取消、50 个告警被确认、50 次重试最终成功。

如果 verify 因为"有 error 记录"就把 `has_integrity_issue` 设为 true，
它就从"不知道"变成了"瞎猜"，而且**猜错的代价比不猜更高**：
用户会去查一个并不存在的问题（这与 `prune` 必须留痕是同一个道理）。

**所以这个功能的核心不是"多给几个数字"，而是"新增信息但不下结论"。**

---

## 三、两层设计（性能与深度分离）

### 第一层 · 分层呈现（默认，零成本）

只按 topic 前缀区分，不需要读任何 payload：

```json
"business_layer": {
  "probe_prefix": "_probe.",
  "dds_events": 0,          // 业务 topic 的事件数
  "dds_topics": 0,
  "probe_events": 20,       // 探针 topic 的事件数
  "probe_topics": 1,
  "probe_detail": [
    {"topic": "_probe.order/settle", "events": 20}
  ],
  "signals": null,          // 第二层未启用
  "note": "业务层数字仅供参考，verify 不对业务逻辑下结论；has_integrity_issue 只反映数据完整性"
}
```

**回答的问题**：我到底采了业务数据还是诊断数据？哪个探针在工作、哪个停了？

### 第二层 · 启发式信号（`--business-signals` 才做）

从探针负载里**粗略地**找 `result=` / `status=` 之后的值：

```json
"signals": {"scanned": 20, "ok": 16, "error": 4, "unknown": 0}
```

**为什么默认关闭**：要扫全量 payload。一个跑了数天的会话可能有上千万条探针记录。

**为什么用启发式而不是要求注册格式**：探针负载是业务自己决定的任意字节
（`docs/13` 的非目标："探针不理解业务语义"）。若这里要求"必须是 JSON 且含 result 字段"，
就把一个可选的分析功能变成了对业务的**格式约束** —— 本末倒置。

## 四、新增的交叉发现：RC-B1

这个功能上线后立刻发现了一个**单看任何一层都发现不了的问题**：

```
dds_events: 0            ← 一条业务数据都没有
probe_events: 20
has_integrity_issue: false   ← verify 说"完整"
```

从"数据完整性"看这没错（该录的都录了，没缺口）。
但从"这个会话能用来复盘业务吗"看，这是**严重误导**。

所以新增一个 finding：

```
[RC-B1][medium] 只有探针数据，没有业务数据
会话里有 20 条探针事件，但没有任何业务 topic 事件 ——
这个会话只能用于诊断，不能用于业务数据复盘。
检查录制时是否用 --exclude-topic 排除了业务 topic，或业务侧当时没有发布数据。
```

**它计入 findings（用户必须看到），但不计入 has_integrity_issue** ——
数据本身没坏，坏的是"这个会话的用途与你预期的不一样"。

**这正是交叉视角的价值**：两个视角并置后，才能发现"两层严重失衡"。

## 五、实现中踩到的三个坑

**① `kInvalidTimestamp = 0`，不是"最早"**

```cpp
TimeRange whole;
whole.begin_ns = 0;   // ← 我以为是"从头"，实际是"无效时间戳"
```

第一版这么写直接段错误（exit 139）。正确做法是用 topic 自己的 `first_ns` / `last_ns`。

**教训**：sentinel value 的语义必须查定义，不能按 POSIX 时间戳的直觉猜。

**② 批量替换只改了一半**

我用字符串替换把循环上界从 `findings.size()` 改成 `findings_with_business.size()`，
**但循环体里的 `findings[i]` 没跟着改**。有 RC-B1 时越界 → 段错误。

编译器不会报（类型都对），只能靠测试或 gdb。

**③ `STRATUM_PROBE` 的 `sizeof` 对指针失效**

我在头文件里写了警告：

> `sizeof(payload)` 只在 payload 是数组时才是长度。传指针会得到 8。

**然后自己的测试代码照样踩了**：

```cpp
STRATUM_PROBE_KV("t", (i < 16) ? "result=ok" : "result=error")
//                    ↑ 三元表达式是 const char*，只发出 7 字节 "result="
```

结果：verify 的信号提取全部 `unknown`，而我以为是分类器写错了。

**修法不是"再写一遍注释"，而是给一个显式的正确入口** ——
新增 `STRATUM_PROBE_STR(topic, cstr)`，用 `strlen`，明确用于指针。

```
STRATUM_PROBE("t", "literal")     → 编译期长度，零开销，推荐
STRATUM_PROBE_STR("t", some_ptr)  → 运行期 strlen，多一次遍历
```

**这是同一类教训的第三次**：
「写在注释/纪律里」防不住错误，要**在 API 或工具层面让错误不可能发生**。

## 六、边界与非目标

| 非目标 | 理由 |
|---|---|
| **判断业务正确性** | verify 不知道业务逻辑 |
| **把业务失败计入 has_integrity_issue** | 那 50 条可能完全是正常的 |
| **要求探针负载是特定格式** | 探针不理解业务语义（`docs/13` 非目标） |
| **默认扫全量 payload** | 性能；用 `--business-signals` 显式开启 |

依赖：

* 探针 topic 的命名前缀可配（`--probe-prefix`，默认 `_probe.`，与 `stratum probe` 一致）
* 业务侧用 `STRATUM_PROBE_STR` 发指针负载（否则会被截断）

## 七、交叉场景的下一步

这个功能是「交叉」的第一块。按性价比排序：

| 优先 | 交叉 | 状态 | 前置 | 价值 |
|---|---|---|---|---|
| **1** | `stratum diff <会话A> <会话B>` | ✅ **已完成**（`docs/15`，12 用例） | 无 | **乘法项**：解锁"回归/变化检测"全部场景 |
| 2 | 回放 + 埋点 + diff = 业务回归测试 | ⬜ 未做 | `play --inject`（core 层） | 回答"改了代码后对同一批历史数据的行为是否一致" |
| 3 | io 诊断包（`export --include-context`） | ✅ **已完成**（CONTEXT.json，6 用例） | 无 | 换机复盘不丢现场 |
| 4 | metrics 加探针指标 | ✅ **已完成**（4 个指标，5 用例） | 无 | 一条告警规则覆盖"数据断了"与"业务没有数据" |

**为什么 diff 排第一**：你想要的每一条交叉，本质都是「把两份东西放在一起看」。
没有"比较"这个动作，交叉只能叫"拼接" —— 两个功能并排跑，但答不出新问题。

**第 2 项为什么还没做**：它依赖 `play` 的 6 个选项（`--inject` / `--loop-count` 等），
那些需要 **core 层改动**（当前 `play` 对它们如实报"暂不支持"）。
在补上 core 能力之前，"回放 + 埋点 + diff"只能做半截 —— 而半截的回归测试比没有更危险
（它会给出"看起来通过了"的假象）。

### 7.1 更新后的四条命令一致性（2026-10-17）

这一轮把「对同一份数据必须自洽」变成了持续验证（`test_xcheck_verify_diff` 等）：

```
verify events=130 == diff 两侧 events=130          ✅
探针分类：verify(60/50) == diff(60/50)             ✅
verify(dds=50,probe=12) == metrics(biz=50,probe=12) ✅
io CONTEXT 的分层 == 上面三个                       ✅
diff 报无差异 ⇒ 两侧 verify 结论一致                ✅
```

**四条命令各说一套数，用户就不知道该信谁** —— 而这种不一致不会报错，
只会让人复盘时对不上账。

**diff 的三个技术难点（必须先裁决，否则做出来的东西会误导人）**：

1. **时间轴对齐**：两次录制起始时刻不同。按绝对时间比毫无意义；要按相对起点或事件序号
2. **条数不同**：1000 vs 980 时怎么比？按序号配对 + 尾部标记缺失
3. **语义差异**：同一 topic 的负载变了但条数没变 —— 要不要比 payload？
