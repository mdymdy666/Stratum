# 13 · 埋点工程需求分析

> **本文的定位**：埋点工程**阶段一**的产出。阶段二（config 增强 + 埋点模块实现）的每一项
> 工作都必须能对回本文的**需求编号**（`PR-xx`）。
>
> **风格**沿用 `docs/07` / `09`：每个场景写清 **谁用 / 触发 / 期望 / 失败 / 影响**，
> 并在末尾给出 **新约束**（`docs/09` 的约定：第一遍定命令，第二遍定例外）。
>
> **核心诉求（用户原话）**：
> > 埋点可以在运行的时候，**自动生成配置文件**，通过**改动配置文件**的方式，
> > 决定 **topic 是否开启**。

---

## 一、要解决的问题

Stratum 现在能零侵入地录**已经发布到 DDS** 的数据。但有一类信息它拿不到：

> **业务进程内部、从未发布到 DDS 的状态**（关键路径耗时、异常分支、状态机跳变、内部计数）。

这类信息只有两条获取途径：
* **改业务源码埋点**（本工程选的路）
* 运行时注入 / eBPF（**已明确排除**，理由见 `docs/12-roadmap.md` 第五节）

**埋点工程的取舍**：接受「改一次源码 + 重启一次」，换取「拿到真正的业务数据」，
并用**配置文件热生效**把后续所有变化成本降到零。

## 二、十二条真实场景

### S01 · 关键路径耗时监控（监控回调）★用户点名

| 项 | 内容 |
|---|---|
| **谁用** | 业务开发者 / 现场运维 |
| **触发** | 在 `submit_order()` 等关键函数内放一个 `STRATUM_PROBE_SCOPE("order/submit")`，进出作用域自动记录 |
| **期望** | 自动发出 `{op, duration_us, result, thread}`；不写 JSON、不构造对象 |
| **失败** | ring 写满 → **丢最旧，业务绝不阻塞**；配置文件不存在 → 用默认值继续，只记一条警告 |
| **影响** | 单次约 **50–100 ns**（一次 memcpy），不引入锁与系统调用 |

**边界分支**
1. **函数抛异常** — scope 是 RAII，析构仍会执行 → **新约束**：`result` 需区分
   `ok / error / exception`，异常路径也必须发一条（否则"最慢的调用"恰恰查不到）。
2. **递归调用** — 同一 scope 嵌套。→ **新约束**：scope 记录**深度**，不做去重。
3. **长函数（数小时）** — 到函数结束才发，期间出问题看不到。→ **新约束**：
   支持 `--max-scope-duration`，超时先发一条 `pending` 记录。

**失败模式**：若业务在信号处理器里调用探针，而 ring 正被读取 → 探针只做无锁写，
**不获取任何可能被信号打断的锁**。→ **新约束**：探针写入路径必须**信号安全**（async-signal-safe）。

**场景交互**：与 S05（采样率）叠加时，scope 的**进入**可以采样、**退出**必须配对，
否则耗时会算错。→ **新约束**：scope 的采样决策在进入时做一次并记住。

**新约束汇总**：`result` 三态 / 记录嵌套深度 / `--max-scope-duration` / 写入信号安全 / scope 采样配对。

### S02 · 数据格式动态指定 ★用户点名

| 项 | 内容 |
|---|---|
| **谁用** | 运维 / 数据分析 |
| **触发** | 改配置 `[topic."order/submit"] format = "json"` → `"kv"` |
| **期望** | **下一条就用新格式**，业务进程不重启、不重新编译 |
| **失败** | 格式名非法 → **不生效，保留旧值**，记警告（不崩业务） |
| **影响** | 格式转换在 **Stratum 读取器侧**做，业务侧无感 |

**边界分支**
1. **业务发的是裸字节** — 探针不解析业务数据，`format` 只影响**读取器如何包装**。
   → **新约束**：`format` 的语义是"**信封格式**"（kv/json/raw），不是"业务负载格式"。
2. **同 topic 两个业务进程用不同 format** — 读取器要能同时处理。
   → **新约束**：格式按**探针实例**区分，而非只按 topic。
3. **format 与负载实际内容不符** — 例如声明 json 但业务发的是二进制。
   → **新约束**：读取器必须**校验并明确报告**，不得静默产出垃圾
   （与 `query --decode` 的四种情形同一原则）。

**失败模式**：格式切换瞬间，读取器可能拿到"半旧半新"的批次。
→ **新约束**：格式变更带**一个生效时间点**，读取器按记录的**写入时刻**判断该用哪个格式。

**新约束汇总**：format 是信封格式 / 按实例区分 / 不匹配必须报错 / 变更带生效时间点。

### S03 · QoS 动态调配 ★用户点名

| 项 | 内容 |
|---|---|
| **谁用** | 运维 |
| **触发** | 现场排查：`reliability = "reliable"`、`depth = 100`；日常：`"best_effort"`、`depth = 1` |
| **期望** | 改配置即切换，**业务进程不动** |
| **失败** | QoS 与对端不兼容 → **报错并保留旧 Writer**，不静默降级 |
| **影响** | 只有 **Stratum 读取器**侧重建 DDS Writer，业务侧零影响 |

**边界分支**
1. **切换时正在发的数据** — 重建 Writer 会丢"在途"消息。
   → **新约束**：切换前先 `Flush` 并报告**丢弃条数**（不假装无损）。
2. **`depth` 调小** — 会**立即丢弃**已排队的旧样本。
   → **新约束**：`depth` 调小按**危险操作**对待（先 dry-run 打印后果），
   与 `prune` / `ctl set --retain` 同一等级。
3. **对端已存在 Writer 用不同 QoS** — DDS 会报不兼容。
   → **新约束**：切换失败时**必须保留旧 Writer 继续工作**，不能让监控断掉。

**失败模式**：QoS 切换失败但配置已改 → 出现"配置说 reliable、实际是 best_effort"的**说谎状态**。
→ **新约束**：`stratum probe status` 必须输出**实际生效的 QoS** 与**配置期望的 QoS**，两者不一致要显式标注。

**新约束汇总**：切换前 Flush + 报告丢弃 / depth 调小按危险操作 / 失败保留旧 Writer / status 报"期望 vs 实际"。

### S04 · topic 动态配置 ★用户点名

| 项 | 内容 |
|---|---|
| **谁用** | 现场工程师 |
| **触发** | 把平时关闭的探针 `enabled = false → true`（如"只在出问题时才采这个"） |
| **期望** | **一个轮询周期内**（≤1s）开始收到数据；关闭同理 |
| **失败** | 配置写错（语法/未知键）→ **不生效，保留旧配置**，记警告 |
| **影响** | 零 —— 关掉的探针在业务侧变成一次 bool 判断 |

**边界分支**
1. **关掉的探针还写数据吗？** — 不写。但**计数**仍要累计（
   → 便于 `status` 回答"这个探针被调用过多少次，只是没发"）。
   → **新约束**：关闭状态保留**丢弃计数**，`status` 可见。
2. **运行期新增 topic** — 配置里出现一个业务还没调用过的探针。
   → **新约束**：配置允许"预声明"，探针首次调用时才注册；两者顺序不定不报错。
3. **删掉一个 topic 段落** — 视为 `enabled = false` 还是"恢复默认"？
   → **裁决**：**视为恢复该探针的默认值**（默认值在自动生成时有记录）。

**失败模式**：配置文件被删 → 探针**继续用内存里的配置**运行，不崩、不静默重置。
→ **新约束**：文件消失 → 保留当前配置 + 警告（**不能突然把监控全关或全开**）。

**新约束汇总**：关闭时保留丢弃计数 / 允许预声明 / 删除段落=恢复默认 / 文件消失保留现状。

### S05 · 高频探针的采样（真实压力）

| 项 | 内容 |
|---|---|
| **谁用** | 业务开发者（不小心埋在了热路径上） |
| **触发** | 某探针每秒被调用 10 万次 |
| **期望** | `sample_rate = 0.01` → 每秒只发 1000 条，**业务开销按同比例下降** |
| **失败** | 采样率写错（>1 或 <0）→ 保留旧值 |
| **影响** | 采样判断本身要**极快**（线程局部计数器，不做全局原子操作） |

**边界分支**
1. **采样必须是"跳过写"，不是"写了再丢"** — 否则开销没降。
   → **新约束**：采样判断必须在 `memcpy` **之前**。
2. **多线程** — 每线程独立计数，避免全局竞争。
   → **新约束**：采样是**每线程**的，总量会略偏离名义值（**必须文档化**，不假装精确）。
3. **`sample_rate = 0`** — 语义是"完全关闭"还是"从不采样"？
   → **裁决**：等价于 `enabled = false`（关闭），并给出提示。

**新约束汇总**：采样在 memcpy 前 / 每线程独立且总量偏离需文档化 / `0` 等价关闭。

### S06 · 紧急熔断（fail-safe）

| 项 | 内容 |
|---|---|
| **谁用** | 运维（发现埋点拖慢业务时） |
| **触发** | 把全局 `enabled` 改成 `false` |
| **期望** | ≤1 个轮询周期内**全部探针静默** |
| **失败** | **配置文件损坏时怎么办？** |
| **影响** | 这是唯一"失败方向必须是安全"的场景 |

**★ 关键裁决（本场景的核心）**

其他所有配置项的错误处理都是"**保留旧值**"，但**全局 `enabled` 是例外**：

> **配置文件解析失败时，全局 `enabled` 取"关闭"** —— 因为运维改配置的动机
> 往往就是"出事了要关掉它"。若此时因为文件写坏而**保留旧值（开着）**，
> 熔断就失效了。

→ **新约束**：全局开关是 **fail-safe 语义**（解析失败 → 关闭）；
其余配置项是 **fail-preserve 语义**（解析失败 → 保留旧值）。**两者必须显式区分并文档化。**

**边界分支**
1. **误判风险** — 配置写坏导致监控全关，可能错过真问题。
   → **新约束**：全局熔断发生时，**必须**在 stderr 打一条高优先级警告
   （"因配置损坏，探针已全局关闭"），并在 `status` 里持续可见。
2. **如何解除** — 修好配置并恢复 `enabled = true`。
3. **业务侧是否感知** — 不感知，探针只是变成 no-op。

**新约束汇总**：全局开关 fail-safe / 其余 fail-preserve / 熔断必须高声告警且 status 可见。

### S07 · 探针自动发现（自动生成配置文件）★核心诉求

| 项 | 内容 |
|---|---|
| **谁用** | 第一次接入埋点的开发者 |
| **触发** | 业务首次调用任一探针，而配置文件不存在 |
| **期望** | **自动生成一份带注释的配置文件**，列出所有已见探针及其默认值 |
| **失败** | 目录不可写 → **用内存默认值继续运行** + 警告（不崩、不阻塞业务） |
| **影响** | 一次文件 I/O（仅首次），之后不影响热路径 |

**边界分支**
1. **生成时机** — 不能阻塞第一次探针调用（那可能在关键路径上）。
   → **新约束**：生成是**异步**的（后台线程或首次轮询时做），首次调用只用内存默认值。
2. **并发多进程** — 三个业务进程同时启动，都发现文件不存在。
   → **新约束**：生成用 **O_EXCL 原子创建**；已存在则**读取**，不覆盖。
3. **新埋点出现** — 业务加了一行新探针，配置文件里没有它。
   → **新约束**：**不自动改写用户文件**（那会破坏人工注释与开关），
   而是：① 该探针用默认值运行；② `stratum probe status` 报告"有 N 个未在配置中的探针"。
   **这是刻意选择**：宁可让人知道，也不悄悄改用户的文件。

**新约束汇总**：生成异步 / O_EXCL 原子创建 / **绝不改写用户文件** / 未配置探针要可见。

### S08 · 配置编辑冲突（复用 `.lock`）

| 项 | 内容 |
|---|---|
| **谁用** | 运维 / 自动化脚本 |
| **触发** | 有人用编辑器改配置文件，同时探针在轮询 |
| **期望** | 读到**半写内容**时**不生效**，保留旧配置 |
| **失败** | 若误读了半写文件，可能**误关闭**某个 topic |
| **影响** | 复用 `config` 模块已有的 `.lock` 编辑锁协议 |

**边界分支**
1. **`.lock` 存在时** — 暂停热重载（不读文件），避免读到半写内容。
2. **`.lock` 是过期锁**（进程已死）— 重载会永久停住。
   → **新约束**：**不能**因为锁存在就无限期不重载；要检测**锁的年龄**，
   超时（如 5 分钟）后**强制重载并告警**（否则一个崩溃的编辑器会让监控永久冻结）。
3. **原子替换**（写临时文件 + `rename`）— 这是最安全的编辑方式。
   → **新约束**：文档推荐 `rename` 式编辑，并说明为什么。

**失败模式**：配置语法错误 → 保留旧配置 + 警告（**除了全局 `enabled`，见 S06**）。

**新约束汇总**：锁存在暂停重载 / 锁超时强制重载 / 推荐 rename 编辑。

### S09 · 多实例隔离

| 项 | 内容 |
|---|---|
| **谁用** | 一台机器上跑多个业务进程 |
| **触发** | 三个业务进程各自带埋点 |
| **期望** | **每个进程有独立的配置与 ring**，互不干扰 |
| **失败** | 默认路径冲突 → 两个进程互相覆盖配置 |
| **影响** | 每进程一份 ring（共享内存段以 pid 区分） |

**边界分支**
1. **默认配置文件路径** — 若都用 `./stratum_probe.toml`，同目录多实例会冲突。
   → **裁决**：默认路径含实例标识（如 `stratum_probe.<pid>.toml`），
   并支持 `STRATUM_PROBE_CONFIG` 环境变量显式指定（多实例共享一份配置时用）。
2. **显式共享一份配置** — 多实例用同一个路径是合理需求（统一开关）。
   → **新约束**：共享是**允许**的，但要能回答"谁在读这份配置"（`status` 列出 shm 段）。
3. **权限** — `/dev/shm` 下不同用户。

**新约束汇总**：默认路径含实例标识 / 支持环境变量覆盖 / 共享配置合法且可观测。

### S10 · 探针与业务数据同轴分析（端到端）

| 项 | 内容 |
|---|---|
| **谁用** | 复盘的人 |
| **触发** | `stratum record` 同时录业务 topic 和探针 topic |
| **期望** | `query --state-at` / `verify` 里两者在**同一条时间轴**上 |
| **失败** | 探针 topic 名与业务 topic 撞名 → 数据混淆 |
| **影响** | 完全复用现有录制/查询/校验链路 |

**边界分支**
1. **命名空间** — 探针 topic 默认加前缀（`_probe.`），避免与业务撞名。
   → **新约束**：前缀可配，但**默认必须加**（安全默认）。
2. **时间戳来源** — 探针用自己的时间戳，业务用 DDS 源时间戳，可能偏差。
   → **新约束**：探针记录**两个时间戳**（写入时刻 + 单调时钟），
   使跨进程对齐成为可能（与 `docs/06` 的"两种时间戳"原则一致）。
3. **探针数据量大时** — 可能淹没业务数据。→ 与 S11 联动。

**新约束汇总**：默认加 `_probe.` 前缀 / 记录双时间戳。

### S11 · 带宽与磁盘保护

| 项 | 内容 |
|---|---|
| **谁用** | 运维 |
| **触发** | 某个探针太吵（每秒数万条），可能写满磁盘 |
| **期望** | 探针流量被限制，**业务数据的录制不受影响** |
| **失败** | 不限流 → 磁盘满 → 业务数据也录不进去（**最坏结果**） |
| **影响** | 限流在**读取器侧**做；业务侧只受 ring 容量约束 |

**边界分支**
1. **`max_rate_hz`** — 超过则丢弃。→ **新约束**：丢弃要**计数并在 status 可见**，不能静默。
2. **优先级** — 探针 topic 与业务 topic 争用同一条录制链路。
   → **新约束**：探针 topic 应可被**单独排除**（`record --exclude-topic '_probe.*'`），
   保证业务数据完整。**这是"宁可少监控，也不能丢业务数据"的取向。**
3. **磁盘水位联动** — 磁盘接近满时先停探针。

**新约束汇总**：限流丢弃要计数可见 / 探针可被单独排除 / 水位联动。

---

### S12 · 配置与负载的一致性校验

| 项 | 内容 |
|---|---|
| **谁用** | 接入调试的人 |
| **触发** | 改了 `format` 或字段声明，但业务发送方式没变 |
| **期望** | **明确报错**并跳过该条，不产出垃圾数据 |
| **失败** | 静默产出错误数据（最坏，因为看起来"有数据"） |
| **影响** | 读取器侧 |

**边界分支**
1. **必须有 reason** — 与 `query --decode` 的四种情形一致：
   `ok / format_mismatch / payload_too_large / unknown_probe`。
   → **新约束**：**每种失败都要有可区分的 reason**，不得笼统"解析失败"。
2. **单条失败不拖垮整体** — 跳过该条继续。
3. **计数** — 失败条数在 `status` / `metrics` 可见。

**新约束汇总**：失败必须有可区分 reason / 单条失败不影响整体 / 计数可见。

## 三、需求条目（阶段二的实现必须对回这些编号）

| 编号 | 需求 | 优先级 | 验收判据 |
|---|---|---|---|
| **PR-01** | 探针库零依赖（纯 C，不链接 DDS） | **P0** | 一个只 `#include` 头文件的 .c 程序能编译并写 ring |

## 四、边界与非目标

**明确不做**：

| 非目标 | 理由 |
|---|---|
| **跨机器共享内存** | 共享内存是机器内的机制。跨机器靠"每台机器一个读取器 + DDS 汇聚" |
| **ptrace 注入 / eBPF uprobe** | 风险不可接受，见 `docs/12-roadmap.md` 第五节 |
| **自动给业务对象序列化** | 探针只搬字节，**不理解业务语义**；要结构化就让业务自己组织 |
| **改写用户配置文件** | 见 S07：宁可报告"有未配置的探针"，也不悄悄改用户文件 |
| **运行时新增采集点** | 埋点是编译期决定的（这是 A 方案的固有属性） |
| **保证不丢** | ring 满了就丢最旧。**"绝不阻塞业务"优先于"不丢数据"** |

**依赖前提**：

* 目标程序**源码可改**（否则只能走 eBPF）
* 可接受**一次重启**（之后所有变化都是热生效）
* 同机部署一个 Stratum 读取器

## 五、与现有 12 组命令的关系

| 命令 | 关系 |
|---|---|
| `config` | **增强**：多层配置、自动生成、fail-safe/fail-preserve 双语义、锁超时 |

## 六、给阶段二的实现顺序建议

```
1. config 增强（PR-05/06/07/08/09）
   → 埋点的"开关"完全依赖它，必须先行
2. 探针库（PR-01/02/03/04）
   → 与 config 解耦，可并行，但先做能让端到端早点通
3. 读取器（PR-10/13）
   → 打通端到端，验证真实价值
4. 可观测性收尾（PR-11/12/14/15/16）
   → status 的"期望 vs 实际"是排障关键，不能省
```

**测试必须随每个 PR 一起交付**（用户明确要求"一个都不能少"）：
大数据量 / 随机（多种子）/ 真实场景 ≥3 三类覆盖 +
热重载正确性 / 崩溃安全 / 零开销（反汇编）/ 端到端，全部进 ctest。

### 7.2 实测性能

```
单条写入           53–68 ns（一次 memcpy + 两次原子操作）
40960 条连续写入   2732 us（环满覆盖，零阻塞）
100000 次写入      68 ns/条
ring 容量          4096 条（每条约 280 字节 → ~1.1 MB）
```

**67 ns 的含义**：一个本来耗时 100 μs 的业务函数，埋点开销是它的 **0.07%**；
即使是 1 μs 的紧函数，也只有 6.7%。可以放心埋在热路径上。

### 7.3 已知边界（**实测数据，不是猜测**）

**① UDP 静默丢包：1000 条量级下约 0~6%**

多次实测到达率：`944 / 961 / 963 / 976 / 995 / 1000`。

值得注意的两个观察：
* **800 条零间隔连发可以全部到达**（dropped=0）
* **1000 条（每 10 条让出 1ms）反而偶尔丢几十条**

说明丢包与"突发"无关，是 DDS 走 UDP + best_effort 的**静默丢包** ——
收不到的报文不会出现在 `dropped` 计数里（收发双方都不知道丢了）。
与 `docs/02-open-issues.md` 的 **O2** 同源。

**因此**：`test_cli_probe` 的规模用例**只断言确定性属性**
（ring 无丢、链路可用、上界不越界），到达率作为**测量值输出**。
拿波动的到达率当通过门槛，会得到一个"今天过明天挂"的断言。

**② 跨机器不支持**

共享内存是机器内机制。跨机器靠"每台机器一个读取器 + DDS 汇聚"。

**③ 需要一次重新编译**

埋点是编译期决定的（见 `docs/12-roadmap.md` 第五节的三选二取舍）。
之后所有变化（开关/格式/采样/QoS）都是热生效。

### 7.4 一个留给后续的改进项

**同一个坑踩了 4 次**：断言人类可读文本时忘了传 `--format table`
（全局 `--format` 默认是 json）。

"写在纪律里"不足以防住它 —— 应该在**测试辅助函数层面消除这个可能性**，
例如提供 `RunCliTable()` 专用于断言人类可读文本、`RunCliJson()` 专用于解析 JSON，
让"忘记传格式"在类型/命名上就变得不自然。
