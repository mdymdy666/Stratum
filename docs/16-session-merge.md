# 16 · 多会话合并（`stratum session merge`）的设计裁决

> **本文的定位**：`stratum session merge` 的**设计前置**，不是使用文档。
>
> **为什么先写这个而不是先写代码**：
> "能合"是工程问题，"**怎么合**"是判断题。裁决错了，合出来的会话就是一个
> **看起来像真的、实际上时间关系是假的**新会话 —— 那比没有这个功能更糟：
> 没有功能时人知道要分别打开两份；有了错误的功能，人会拿合并结果去做
> "两个节点在同一时刻看到了什么"的判断。
>
> **对应实现**：`src/cli/cmd_merge.cc`；测试：`tests/integration/test_merge.cc`。
>
> **一句话结论**：合并**不做任何推测性修正**。它只做三件事 ——
> 取一条共同的时间轴、把同名话题放在一起、把跨源完全相同的记录去掉。
> 冲突、时钟偏差、丢弃，全部**只报不改**。

---

## 一、要解决的问题

现在 Stratum 能分析**单个**会话。真实部署里数据天然分散：

| 问题 | 现在能不能答 |
|---|---|
| 两个节点同时录，同一份广播各自收到了什么？ | ✗ 只能分别 query 再人工拼时间 |
| A 节点在 14:03:22.100 收到的那条，B 收到了吗？ | ✗ 两份会话各在自己的时间原点上 |
| 一次故障里，网关和终端两侧的记录能不能拼成一条时间线？ | ✗ 没有"合并"这个动作 |
| 同一 topic 在两个会话里都有，合起来到底多少条？ | ✗ 只能手算，还得先想清楚重复怎么算 |

**这一切的共同动作是"把多份放到同一条时间轴上"。**

---

## 二、★ 裁决 1 · 时间轴对齐用哪个时钟？

### 问题

每条事件有两个时间戳（见 `docs/06-data-trust.md`、`src/include/stratum/core/types.h`）：

| 时间戳 | 来源 | 特性 |
|---|---|---|
| `source_timestamp_ns` | **发布端**打的（随 DDS 样本传播） | 同一条消息在 A、B 两份录制里是**同一个数值**；但不同发布者可能各用各的钟 |
| `reception_timestamp_ns` | **接收端**录制器本地钟 | 同一台机器内一致；但 A、B 的收包时刻必然不同（差一个网络往返 + 调度延迟） |

同一份广播被两个节点录到时，这两个时间戳的行为完全不同：

```
发布者 @ t=1000 发一条
  节点 A: source=1000  reception=1000.30
  节点 B: source=1000  reception=1000.92   ← 与 A 不同（网络 + 调度）
```

### 裁决：**用 `source_timestamp_ns`，且按绝对值合并，不做重定基**

```
merged_ts = source_timestamp_ns + 该源的 --offset（默认 0）
若 source 无效（== 0）→ 退化为 reception_timestamp_ns，并计数
```

三条理由：

1. **只有 source 能让同一条消息在两个源里落在同一时刻。**
   这是合并的目的本身：重建"两个节点在同一时刻各自看到了什么"。
   用 reception 对齐，同一事件会被网络抖动拉开一个不确定的量 ——
   **误差正好等于我们想消除的东西**。
2. **reception 的语义是"本机收到"，不是"事件发生"**。
   拿它当合并轴，等于断言"A 收到的那刻 B 也收到了"，与事实不符。
3. **绝对轴才有物理含义**。重定基（把每个源的起点对到全局最早起点）会得到
   一条"形态可比、时刻是假的"轴 —— 那是 `diff` 的领域（`docs/15` §二），
   不是 `merge` 的。合并的产物要能被 `query --state-at` 当作真实时刻查询。

### 时间戳不是"修正"出来的：显式 `--offset`

各节点的源时钟不一定同步（无 PTP / chrony）。合并**不自动检测并校正**，只提供：

```
--offset <会话>=<±时长>     例: --offset /data/nodeB=-100ms
```

`--offset` 是**人给出的断言**："我认为 B 的钟快了 100ms"。工具照做，并在报告里
记录 `offset_ns`（可审计）。**为什么不做自动校正**：自动校正会在时间轴上
**编造**一个谁也没测过的偏移；一旦猜错，合出来的"同时"是假的，而且看不出来
（这正是 §五 那条护栏的延伸）。

### 报告里必须有"观测到的偏差"

不去自动校正 ≠ 什么都不说。合并时会**测**：如果同一话题、同一 payload 哈希的记录
在两个源里出现了不同的时间戳，两者之差就是"同一份数据被两个源记在不同时刻"的证据。

```json
"alignment": {"skew": {"samples": 120, "min_ns": 99920000, "max_ns": 100080000,
                       "median_ns": 100000000, "warning": true}}
```

**这只是观测，不是判定**：它也可能是"同一条 payload（例如心跳/恒定温度）
隔了一段时间又发了一次"。所以报告用 `samples/min/max/median` 而不是一个
"偏差 = 100ms"的结论，并把它和 `--offset` 的用法写在一起。

判据（可执行的信号）：

```
|median_ns| > 1ms  或  (max_ns - min_ns) > 1ms  →  clock_skew.warning = true
```

### 一个具体数字的例子：50ms 钟差到底会影响什么

先把"**谁的钟**"说清楚，因为两种情况结论完全相反。

**情况 A：同一个发布者、两个节点各自录制（广播场景）** —— 录制端钟差 **不影响**合并。

`source_timestamp_ns` 是**发布者**打的，随样本传到两个接收端；`recorder.cc` 只在
source 缺失时才退化为 reception。所以 A、B 两份录制里同一条消息的 source 是**同一个数**：

```
发布者钟: t=1000.000 发一条
  nodeA: source=1000.000  reception=1000.030   ← A 的本地钟
  nodeB: source=1000.000  reception=1000.075   ← B 的本地钟（与 A 差 45ms）
合并后: 一条 @1000.000（reception 原样保留，不参与对齐）
```

**这正是裁决①选 source 的直接收益**：接收端钟差 45ms，合并结果一点都不偏。

**情况 B：两个节点各自发布（各用各的钟）** —— 钟差 50ms 会**原样进入**合并时间轴：

```
真实时刻 T=1000.000
  nodeA 发 sensor/a（A 钟准）       → source=1000.000
  nodeB 发 sensor/b（B 钟快 50ms）  → source=1000.050
合并后: a@1000.000, b@1000.050 —— 被排成"b 在 a 之后 50ms"
```

后果（也就是下文三条局限的具体化）：

* `query --state-at @1000.020` 只返回 a（b 还没"到"），真实情况是两者同时；
* 若 b 是 a 的响应（真实因果间隔 0ms），合并后会读到"响应晚了 50ms"——
  **因果顺序可能反转**；
* 若两个节点都转发同一份广播（两条 publisher 各自序列化），source 差 50ms
  会让去重失效、条数翻倍；
* 修正：`--offset /data/nodeB=-50ms`。报告里 `offset_ns=-50000000` 是这次校正的
  审计痕迹，`clock_skew.median_ns=50000000` 是它的证据。

### ★ 必须同时写进文档的局限（不能只写在代码注释里）

> **① 发布端时钟不同源时，跨源的时间先后与间隔不可信。**
>
> 合并保留的是**各自时钟读数**的拼接，不是同一个物理时钟。若 nodeA 与 nodeB
> 的钟差 100ms，合并会话里 A 的每一条都会比"真实同时"的 B 早/晚 100ms。
> 后果具体是：
>
> * 同一份广播的**去重会失效**（时间戳不等 → 判成两条，条数翻倍）；
> * `query --state-at` 在两家交界处会给出**错误的状态**（把还没到的消息算成已到）；
> * 跨节点"谁先谁后"的判断**不可信**（差值小于钟差时，先后关系可能反转）。
>
> 注意：**如果两个源录的是同一个发布者，接收端钟差不会造成这个问题**（见上一节
> 情况 A）。这条局限针对的是「不同发布者」或「source 缺失、退化为 reception」。
>
> 此时唯一正确的做法是 `--offset` 校正，且**校正量必须有来源**（PTP 日志、
> NTP 偏差、或用 `clock_skew.median_ns` 作为证据并写进报告）。
>
> **② 时钟跳变会被合并"抹平"。**
> 源时间戳倒退时，存储层仍按时间戳排序；合并再按时间戳归并一次，
> 于是"录制时发生过一次时钟跳变"这件事在合并会话里**看不出来**。
> 要查时钟问题，必须回到源会话看 `verify` 的 `timestamp_regressions`，
> 合并报告里每个源都带了这个计数。
>
> **③ 合并不改善精度，只会传递精度。**
> 如果源本身录制时丢了 40% 数据，合并后那段空洞仍然在（甚至因为去重看起来"更整齐"）。
> **合并后的 `verify` 结论只能评价合并产物，不能反推源是否完整。**

## 三、★ 裁决 2 · 同一 topic 在多个会话里都有数据，合并后怎么表示？

### 问题

三个方向：

| 方向 | 做法 | 问题 |
|---|---|---|
| **合成一个 topic** | `sensor/imu` 仍是 `sensor/imu`，事件按时间归并 | 单个事件看不出来自哪个节点 |
| **按来源加前缀** | `nodeA/sensor/imu`、`nodeB/sensor/imu` | **topic 名被改写**，下游全部语义错位（见下） |
| **按来源分开存** | 源 1 的 topic 用 topic_id 1，源 2 的同名 topic 用 id 2 | 同一个 DDS topic 被拆成两个，条数/速率/状态查询全部要人再合并一次 |

### 裁决：**合成一个 topic，名字原样保留；来源信息进报告，不进名字**

```
目标会话里 sensor/imu 只有一个 topic，事件 = 各源该 topic 的事件按时间归并（去重后）
每个源的贡献量、时间范围、偏移 → 只出现在合并报告里
```

**为什么拒绝"加前缀"**（这不是风格问题，是会直接弄坏三件已工作的功能）：

1. **探针分类会失效。** 业务层用前缀 `_probe.` 判定探针 topic（`docs/14`）。
   `_probe.agent/heap_used` 加上节点前缀后不再以 `_probe.` 开头 →
   `verify` / `metrics` / `diff` 会把探针数据当业务数据统计。
2. **`diff` 会退化成全量新增/消失。** `diff` 按 topic 名配对（`docs/15`）。
   改名后 `sensor/imu` → `nodeA/sensor/imu`，两份会话的 topic 集合**无一相交**，
   报告变成"全部 added、全部 removed"，这正是 diff 存在的意义被抹掉。
3. **`query` 的既有脚本会查不到。** 用户和脚本按真实 DDS topic 名查询；
   改名等于要求所有人改脚本，而改名后的名字在 DDS 世界里**并不存在**。

**代价（必须承认）**：合并产物**不保留逐事件来源**。合并会话回答的是
"这条时间轴上发生过什么"，不是"这条是谁记的"。需要逐源归因时，
报告里有每个源的事件数/时间范围/偏移，源会话本身也还在（合并是**新增**一个会话，
不删不改任何源）。

**同名 topic、不同内容**：两个节点上同名 topic 实际是两条不同的数据流
（例如两个 publisher 用了同一个 topic 名）。工具**不判断谁对**，两个都保留，
并在 `conflicts` 里计数（定义见 §四）。

## 四、★ 裁决 3 · 去重按什么？

### 候选

| 键 | 能不能用 | 为什么 |
|---|---|---|
| `(topic, seq)` | ✗ | `seq` 是**录制器本地分配**的（`types.h` 明写"由 Recorder 分配"）。A 的 `seq=42` 与 B 的 `seq=42` 完全可能是两条不同消息，按它去重会**误删真实数据** |
| 只看 payload 哈希 | ✗ | 同一条 payload 在不同时刻重复出现是常态（心跳、恒定温度）。按内容去重会把**真实重复发布**删掉 |
| `(topic, reception_ts)` | ✗ | reception 是各节点本地钟，同一广播在 A、B 的 reception **永远不相等**（差一个网络延迟） |
| **`(topic, source_ts, payload_hash)`** | ✓ | 同一条广播在 A、B 里：topic 相同、source 时间戳相同（发布端打的）、payload 字节相同。三者同时相等才判重复 |
| 不去重 | ✓（选项） | `--dedupe none`：我就是要看"总共收到几次" |

### 裁决：**`(topic, source_timestamp_ns, payload_hash)` 三元组，仅跨源去重，默认开启**

```
--dedupe content   （默认）跨源完全相同 → 只留一条
--dedupe none      全部保留（条数 = 各源之和）
```

**广播场景下 A、B 都收到同一条，合并后应该是**一条**。理由：

1. **它在物理上只有一条。** 合并会话的语义是"这条时间轴上发生过哪些消息"，
   不是"被几个接收端收过"。留两条会让条数变成**接收次数**。
2. **留两条会污染所有下游计数。** `query` 的条数、`metrics` 的速率、
   `diff` 的分桶、`verify` 的采样率判断全部翻倍，而且看起来完全正常 ——
   这是最坏的一类错误：数字自洽，含义错了。
3. **"哪些节点收到了"这个信息不该用重复事件表达。** 它是**来源覆盖度**，
   在报告里（每个 topic 的 `sources` 计数、每源的 `contributed`）。

### 同源内**不**去重

同一个录制器在同一时刻记录的两条相同 payload 是**两条真实事件**
（重复发布、样本重传）。删掉它就是篡改数据。所以去重集合只在
**不同源之间**生效：判定时看"这条记录是否已由**另一个**源写过"。

### 冲突计数（同名同刻不同内容）

```
conflicts = 同一 topic、同一（合并后）时间戳、但 payload 哈希来自不同源且不同
```

两条都保留，只计数。它通常意味着"两个节点上的同名 topic 是不同数据流"。
工具**不判断谁对**（§五），只在报告里让这个事实可见。

### 哈希与碰撞的诚实说明

* 用 FNV-1a 64（与 `cmd_diff.cc` 同一算法，跨机器稳定；`std::hash` 标准没规定算法，不用）。
* 不去逐字节比较：合并本来就要把事件读进内存，但逐字节比会让去重从
  O(n) 变成"每条都要和候选集比一遍"；用哈希 + 精确时间戳 + topic_id，代价是
  **碰撞概率**（n 条记录时约 n²/2⁶⁵）而不是确定正确。
* 碰撞的后果是**少了一条真实记录**（被误判为重复）。这个风险写在文档里，
  不藏在代码里；对 10⁶ 条量级，概率约 3×10⁻⁸，可接受。

### payload 只差一个字节会怎样（已被问到的风险，正面回答）

同一份广播在两个接收端拿到的 payload 字节**应当完全相同**（DDS 交付同一份
序列化字节）。但如果两个源拿到的不是同一份字节 —— 不同 publisher 各自序列化、
中间有代理/网关重编码、录制端按大小截断、schema 版本不同 ——
哈希就不同，同一条广播会被判成**两条**，条数偏高。

**这个方向是刻意选的，不是疏忽：**

| 判错的方向 | 后果 | 可见性 |
|---|---|---|
| 误判"不同"（字节差 1 个） | 少去重，条数偏高 | **可见**：`duplicates_removed=0` 与 `events` 对不上 |
| 误判"相同"（哈希碰撞） | 删掉一条真实记录 | **不可见**：数据少了，没有任何信号 |

宁可少去重。这与 §五 的护栏一致：工具**没有能力**判断"这两段字节算不算同一条"，
所以它只在**能证明相同**（topic + 时间戳 + 哈希三者全等）时才合并。

**怎么发现**：若你确信两个源录了同一份广播，但 `dedupe.duplicates_removed == 0`，
按可能性排查：

1. 时钟偏差 —— 看 `clock_skew`（有样本就说明同内容出现了不同时刻）；
2. payload 字节差异 —— 用 `query <源> --topic <名> --with-payload` 两份对照。

工具**不会**自动剥离 CDR 封装、不会做模糊匹配、不会"差几个字节也算同一条"——
存储层不理解 payload 内容（`docs/11`），要求它理解就破坏了分层。
确实需要"近似去重"时，正确做法是先用 `--dedupe none` 把全量合进来，
在上层用真正理解 payload 的工具处理。

## 五、★★ 核心约束：**合并不判断数据对错**

### 这是整个功能的护栏

```
合并不修正时间戳、不补齐空洞、不删除"看起来不对"的记录、不判断哪个源可信。
它只把多份放在同一时间轴上。
```

**与 `verify` 的"不给业务逻辑下结论"（`docs/14`）、`diff` 的"不判断变好变坏"
（`docs/15` §五）是同一条原则。**

### 为什么必须守

合并会碰到一堆"看起来可以顺手修一下"的情况：

| 情况 | 顺手修一下的诱惑 | 为什么不修 |
|---|---|---|
| 两源时间戳差 100ms | 自动对齐 | 偏移量是猜的，猜错看不出来（§二） |
| 某段两源都没有数据 | 插一条"缺失"记录 | 空洞是事实，不是记录；插进去会伪造数据 |
| 同名 topic 内容不一致 | 选一个"更可信"的 | 工具不知道谁是权威 |
| 一条 payload 只在一个源出现 | 判为"另一源漏了" | 可能那条本来就没被另一个节点订阅 |

**合并的错误模式不是"报错"，而是"安静地给出一个自洽的假时间轴"。**
这条护栏就是防它。

### 实现要求：输出里**必须有** `note` 字段

```json
"note": "合并不判断数据对错，只把多份放在同一时间轴上 —— 不修正时间戳、不补齐空洞、不删除源数据（仅跨源完全相同的重复记录会合并为一条）；冲突与时钟偏差只报不改，是否可信请结合上下文判断"
```

**这句不是客套，是契约的一部分。**

## 六、输出契约

### 命令形态

```
stratum [--format table|json] session merge <会话1> <会话2> [...] --to <目标会话> [选项]

选项:
  --to <路径>              目标会话（必填）。不存在则新建；已存在且非空 → EXISTS(3)
  --overwrite              目标非空时先清空（危险操作，必须显式）
  --dedupe content|none    去重策略（默认 content）
  --offset <会话>=<±时长>  给某个源加固定偏移（可重复），用于时钟偏差校正
  --report <文件>          额外把合并报告（JSON）写到文件
```

### JSON（默认；全局 `--format` 非 TTY 时为 json）

```json
{
  "schema_version": 1,
  "target": "/data/merged",
```

| 码 | 含义 |
|---|---|
| **0** | 合并成功，无告警 |
| 1 | ERROR（写目标失败） |
| 2 | USAGE（参数不足 / 目标与源相同 / 选项非法） |
| 3 | EXISTS（目标已存在且非空，未给 `--overwrite`） |
| **5** | **PARTIAL**：合并完成，但**有冲突或有可疑时钟偏差** |
| 6 | ENV（源会话打不开 / 目标目录不可写） |

## 七、边界与非目标

| 非目标 | 理由 |
|---|---|
| **自动检测并校正时钟偏差** | 会编造没人测过的偏移（§二） |
| **相对重定基（把各源起点对齐）** | 那是 `diff` 的相对对齐；合并要保留绝对时刻（§二） |
| **按来源改写 topic 名** | 破坏探针分类 / diff 配对 / 现有查询脚本（§三） |
| **保留逐事件来源** | 存储层 Event 没有来源字段；加字段等于改磁盘格式。覆盖度在报告里 |
| **补齐空洞 / 插"缺失"标记** | 空洞是事实，不是记录（§五） |
| **增量合并 / 合并到已存在的会话** | target 已存在默认拒绝；要重来就 `--overwrite` 全量重建 |
| **近似时间去重（窗口匹配）** | 只判"完全同一时刻"；偏差请先 `--offset` 校正再用默认去重 |
| **跨机器时钟同步** | 超出工具职责；`--offset` 是人给出的断言 |

**依赖前提**：

* 每个源都是可打开的会话（`TimelineImplV2::Open` 成功），且**不被并发写入**（合并读的是静态快照）
* 目标路径与任何源路径不同

**已知资源开销**（诚实说明）：

* 去重需要把每个话题的事件读进内存后按时间排序 —— 峰值内存 ≈
  **所有源 payload 总量** + 每事件约 80 字节。百万级会话需要数 GB。
* 去重集合每条 20 字节键 + 哈希表开销。10⁶ 条约 50–80MB。
* 这两条是"按绝对时间归并"的必然后果（按源顺序追加会让时间戳倒退，
  污染合并会话的 `timestamp_regressions`）。

## 八、与现有命令的关系

| 命令 | 关系 |
|---|---|
| `query` | **复用** `ListTopics` / `FindTopicByName` / `QueryRange`；合并后按真实 topic 名可查 |
| `verify` | **独立**：合并会话的 quality 是重新累积的（丢弃=0、倒退=0），**不能反推源质量**；源的质量在报告的 `sources[].quality` 里 |
| `diff` | **可直接对比**：合并会话与源会话 topic 名一致，单源合并应与源"无差异"（测试用它当硬判据） |

| `play` | 回放合并会话 = 把多节点数据放到同一条时间轴上重放；时间关系由 §二 的裁决决定 |
| `io` | 无关（合并的是活会话，不是 bundle） |
| **`merge`（新增）** | 唯一定位：**把多份会话放到同一条时间轴上**，并报告冲突/重复 |

## 九、测试计划（进 ctest，10 个用例，65 → 75）

| 用例 | 验证什么 |
|---|---|
| **SingleSourceIsCopy** | 单会话合并 ≡ 复制：`diff 源 合并产物` 退出码 0、条数/topic 一致、产物无完整性问题 |
| **DisjointTimeline** | 两源无时间重叠 → 条数 = 之和、`span` = 并集、`first/last_ns` 精确 |
| **★ BroadcastDedup** | 两源都收到同一批（同 topic/ts/payload）→ 合并条数 = 1 份、`duplicates_removed` 精确、退出码 0；`--dedupe none` 全保留 |
| **★ SameSourceNotDeduped** | 同源同刻同内容 3 条全保留，只有跨源的 1 条被去掉（去重只在跨源生效） |
| **★ ClockSkewOffset** | B 的源时间戳整体 +100ms：默认 → 重复判定失效（条数翻倍）+ `skew.warning=true`；给 `--offset B=-100ms` → 去重生效、条数回到 1 份 |
| **EmptySource** | 空会话参与合并（一空一非空 / 两空）→ 不崩、条数正确、空源 `contributed=0` |
| **TenSources** | 10 个源 → 条数 = 1000、每源 `contributed` 正确、topic 覆盖度 10、产物可查 |
| **SameTimestampDifferentPayload** | 同名同刻不同 payload → `conflicts` 精确、两条都保留、退出码 5（PARTIAL） |
| **CliErrors** | 源不存在→8 且不创建目标、目标已存在→3、`--overwrite` 重建、参数不足/缺 `--to`/目标==源/非法选项→2 |
| **TableMatchesJson** | `--format table` 有人类可读文本（含说明）且与 JSON 条数一致 |

**最有价值的三个**：`BroadcastDedup`（去重规则是否成立）、`SameSourceNotDeduped`
（去重不能越界删源数据）、`ClockSkewOffset`（对齐规则的失效边界是否**可观测**）——
它们是"合并"与"瞎拼"的分界线。

## 十一、实现时定死的三个口径（写代码时才必须回答的问题）

裁决文档给了方向，但**"同内容"到底怎么算、偏差到底怎么测**在写代码时必须给确切答案。
这一节记录当时的决定，避免下一个读代码的人重新猜一遍。

### ① 时钟偏差的观测口径：同 payload、跨源、时间相邻配对

两个源的"钟差"没法直接测（没人知道真实时刻）。能测的只有：

```
同一 topic、同一 payload 哈希、来自不同源的两条记录，时间戳之差
```

实现上按话题内 `payload 哈希 → [(ts, src)]` 分组，排序后取**时间上相邻且跨源**的配对。
统计量用 `min / max / median`，不用"平均偏移"。

**为什么用中位数**：重复内容（心跳、恒定值）会把个别配对的差拉大；
中位数对这类污染稳健。**为什么不用平均**：一个离群值就能把"看起来同步"变成"看起来偏 1 秒"。

**一个必须承认的后果**：`samples == 0` 时报告写"无法观测，不代表没有偏差"——
没有同内容样本时，工具**没有任何证据**，不能反过来说"时钟是同步的"。

### ② 冲突的精确口径：同刻、跨源、与"首个记录"内容不同

```
同一 topic、同一（合并后）时间戳、payload 哈希不同、且来自另一个源 → conflicts + 1
```

**为什么不用"时间窗内的相似匹配"**：窗口大小要猜。窗口给小了漏报，给大了把
"两个节点各自产生的内容"误判成冲突 —— 与 §五 的护栏直接冲突（宁可少报，不可猜）。

### ③ 写入顺序：按时间排序后追加（否则 `verify` 会报假故障）

第一版如果按"源 1 全部、源 2 全部"追加，第二个源的早期事件会落在第一个源晚期事件之后，
存储层会把它记为 **时间戳倒退** —— 合并产物 `verify` 报 RC 类问题，
而真正的原因是**我们自己的写入顺序**。

所以：每个话题在内存里按 `(合并后时间戳, 源序号, seq)` 排序，再分批 `AppendBatch`。
代价是峰值内存（§七已写），换来的是"合并产物自身是干净的"这条可测性质
（测试断言 `has_integrity_issue=false`）。

### ④ 一个被测试纠正的预期（如实记录）

写测试时我先假设"两个无时间重叠的会话合并 → 一定退出码 0"。
第一版测试两个源都用了相同的 payload 序列（`x0..x99` / `x0..x79`），
结果是 **5**：因为这恰好构成"同内容、跨源、恒定 5.99s 偏差"——
工具无法区分"时钟偏了 6 秒"和"两个独立数据流碰巧内容相同"。

**修正的是测试，不是实现**：两个独立数据流应当用不同的 payload（真实场景里
它们本来就不同）。这条写在这里，是为了说明 **PARTIAL(5) 的语义是"有可疑信号"，
不是"确定有偏差"** —— 保守提示，宁可信其有。
