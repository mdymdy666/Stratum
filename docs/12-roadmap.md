## 四、沉淀的设计原则

1. **主动行为必须留痕** —— `pruned/`（裁剪）、`control_events`（主动停止）、
   `typedef/`（类型注册）都要能与"故障"区分，否则事后复盘会去查**不存在**的问题。
2. **独立 meta key + 追加式 + 接口默认实现返回 `NotSupported`** ——
   三处验证过的模式，**不改动既有编码格式**。
3. **不要把天然易变的东西当作不变量** —— LSM 文件清单会漂移（已亲眼见证）。
4. **降级是常态，不是异常** —— DDS 的 SEDP 不保证携带类型定义。
5. **危险操作默认安全** —— `prune` 默认 dry-run；`import` 默认不覆盖。
6. **诚实胜于好看** —— 修不了就说修不了；有损就写成断言；**结论对但工具错也要修**。

## 五、⚠️ 用户提出的期望（原文记入，不得丢失）

### 用户原话（2026-10-15）

> **我推荐 hook 和 eBPF 配合注入，就是运行中的 C++ 程序，利用 topic 动态搞定检测**

### 环境实测（2026-10-15，非印象）

```
内核 6.6.87.2-microsoft-standard-WSL2
BTF:                       ✅ 存在（6MB）—— CO-RE eBPF 前提满足
tracefs:                   ✗ /sys/kernel/debug/tracing 未挂载（/sys/kernel/tracing 在）
bpftrace / bpftool / perf: ✗ 均未安装（clang ✅）
unprivileged_bpf_disabled: 2      ← 非特权 eBPF 完全禁用
CapEff:                    0000000000000000  ← 当前进程无 capability
uprobe 试挂:               ✗ 失败
```

**结论**：可行，但需要 `sudo` + 装工具 + 手动挂 tracefs；**不是拿来就用**。

### 评估：方向对了一半

**✅ 对的部分**：**「利用 topic 动态搞定检测」是真正的方向**，且**不需要 eBPF**。
因为 topic 信息 Stratum 已完全掌握，缺的是**分析层**而不是**采集手段**。

**⚠️ 需要修正的部分**：**eBPF/hook 不是必需的**。关键事实：

> **Stratum 自己就是 DDS 参与者**，通过 SPDP/SEDP **自动发现**话题 ——
> **不需要 hook 目标进程，就能录到它发布的全部数据。**

所以 eBPF 的**边际价值只在一种情况**：**目标进程内、尚未发布到 DDS 的数据**
（内部中间变量、只在进程内传递的状态）。**这个场景真实，但窄，且脆弱。**

### 一个必须保留的区分

| | 手段 | 安全性 | 归属 |
|---|---|---|---|
| **观测**（只读） | eBPF uprobe / tracepoint | 安全 | **采集层**（扩数据源） |
| **注入**（写） | hook 改行为 / 故障注入 | **危险，仅限测试环境** | **测试层**（`play --inject` 的领域） |

用户举的例子（动态检测）属于**观测**；若扩展到"注入修改运行中程序"，
在生产系统上是高风险动作，必须严格隔离。

## 六、下一步任务

### 第 1 层 · 建议先做：`stratum watch`（topic 行为分析）

**零新依赖** —— 用已有数据（`query` / `metrics` / 类型定义）算行为基线。

| 检测项 | 判据 | 依据 |
|---|---|---|
| **话题静默** | 该发不发（如 100ms 周期话题 2s 无数据） | 时间戳序列 |
| **频率漂移** | 实际间隔 vs 历史基线偏离 | 时间戳序列 |
| **值域越界** | `temperature > 120` | **需要 `--decode` + 类型定义**（已有） |
| **新话题出现** | 未注册话题开始发布 | `session` / `types list` |
| **完整性劣化** | `integrity_issue` 从 0 变 1 | `metrics` |

**价值**：**从「事后查」到「事中提醒」** —— 这才是"动态检测"的实质。
**天然可接**：输出 Prometheus 指标，直接写告警规则。

**为什么放第一**：不需要新基础设施就能回答"这个系统现在健康吗"——
这是黑匣子场景最常被问的问题。**先证明分析层有人用，再解决采集层盲区。**

### 第 2 层 · eBPF uprobe：采集"进程内未发布数据"

**形态**：`ISource` 的**可选实现**（与项目插件化后端一致）。

**两个必须正视的风险**：
1. **uprobe 依赖符号偏移** —— C++ `-O2` 内联后符号消失 → **抓不到**。
   这与"长期常开"的稳定性要求**冲突**。
2. **需要特权** —— 生产部署要开 `unprivileged_bpf_disabled` 或给 capability。

**前置动作**：先写一个**环境可行性验证**（`sudo` 挂 uprobe 到一个真实 DDS 程序，
看能否抓到进程内数据）—— **需要用户确认，因为要提权**。

### 第 3 层 · 跨机因果 + 时钟对齐

eBPF 在这层价值更大（tracepoint 抓网络/调度），但依赖前两层先扎实。

## 八、方法学纪律（下轮必须遵守）

**校验自身也会错 —— 本阶段栽了 4 次**：
1. 只比字符串先后没查语义结构 → `return` 落进 `for` 体内（**单话题测不出来**）
2. 相邻行匹配因中间有空行而落空，脚本却报成功
3. 匹配到**注释里的示例文本**
4. 检查字符串带了多余的引号

**其他已踩过的**：

* **heredoc 必须用 `<<'EOF'`（带引号）** —— 用 `<<EOFX` 会让记录里的**反引号被
  shell 当命令执行**。稳妥做法：**用 `write` 写文件再 `cat` 追加**。
* **搬移代码块必须用括号计数**定范围（`awk '/^}$/'` 会匹配到内层 `}`）。
* **涉及"逐项遍历"的逻辑，测试数据必须 ≥2 项**。
* **引用文档前必须核对它存在**（曾引用不存在的 `docs/03-open-questions.md`
  并虚构「Q4」编号）。
* **提交成功 ≠ 推送成功** —— 502 需带退避重试（10/20/30 秒）。
* **`grep -c` 计数为 0 时退出码是 1** —— 不要写 `|| echo 0`。
* **`enum class` 不能直接喂 `STRATUM_CHECK_EQ`** —— 用 `static_cast<int>`。
* **全局 `--format` 默认是 json** —— 专用命令应输出自己的自然格式。
* **`/tmp` 会被系统定期清理** —— 实测会话放 `$HOME`。
* **`TimelineImplV2` 所有公开方法：`if (!opened_)` 必须在 `lock_guard` 之后。**
