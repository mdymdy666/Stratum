# 15 · 会话对比（`stratum diff`）的设计裁决

> **本文的定位**：`stratum diff` 的**设计前置**，不是使用文档。
>
> **为什么先写这个而不是先写代码**：
> "能比"是工程问题，"**怎么比**"是判断题。裁决错了，做出来的 diff 会给出**误导性结论** ——
> 那比没有这个功能更糟：没有功能时人知道要自己算，有了错误的功能人会信它。
>
> **对应实现**：`src/cli/cmd_diff.cc`；测试：待加。

---

## 一、要解决的问题

现在 Stratum 能分析**单个**会话，但答不出这类问题：

| 问题 | 现在能不能答 |
|---|---|
| 部署前后，数据流有没有变化？ | ✗ 只能人肉两条命令各跑一遍再对比数字 |
| 改了业务代码，探针指标变了多少？ | ✗ 同上 |
| 这次的会话和上次基线比，少了哪些 topic？ | ✗ 同上 |
| 两次录制的耗时分布是否一致？ | ✗ 没有分桶统计 |

**这一切的共同动作是"把两份东西放在一起看"。**

没有"比较"这个动作，前面做的埋点、类型系统、verify 业务层只能"拼接"，
不能组合出新结论。

---

## 二、★ 裁决 1 · 时间轴对齐

### 问题

两次录制的绝对时刻必然不同：

```
会话 A：2026-10-17 14:03:22.100 开始    (ts = 1792...100)
会话 B：2026-10-17 16:47:05.900 开始    (ts = 1792...900)
```

直接按绝对时间比 —— 所有事件都不在同一时刻，**diff 会报"100% 不同"**。这毫无意义。

### 裁决：以**相对时间**对齐

```
左会话 origin_A = min(所有 topic 的 first_ns)
右会话 origin_B = min(所有 topic 的 first_ns)
比较坐标 = event_ts - origin（各自的）
```

输出里必须显式给出：

```json
"alignment": {
  "mode": "relative",
  "left_origin_ns": 1792228100100000000,
  "right_origin_ns": 1792229225900000000
}
```

### ★ 必须同时写进文档的局限（不能只写在代码注释里）

> **相对对齐能比"时长与分布"，但不能断言"两次录制的第 N 秒发生的是同一件事"。**
>
> 举例：A 录了 10 秒、B 录了 10 分钟。相对对齐后，
> 把两条时间轴都拉伸到 [0,1] 比较 —— 这会让 **A 的早期差异被放大**、
> **B 的后期细节被压扁**。
>
> 因此：**两侧时长差异超过一个数量级时，分桶对比的结论不可信。**
> 工具应当在这种情况下**主动警告**（见 §六 的 `duration_warning`）。

**这条局限是相对的，不是缺陷** —— 绝对对齐根本不可用，逐条对齐不成立，
相对对齐已经是唯一可行的选择。但它的失效边界必须让人知道。

## 三、★ 裁决 2 · 条数不同怎么比（1000 vs 980）

### 问题

三个可能的方向：

| 方向 | 做法 | 问题 |
|---|---|---|
| **事件级逐条** | 像 git diff 那样对齐第 i 条 | 时序数据逐条比**只产噪音**：两次录制的时序必然不同 |
| **只比总数** | 报 1000 vs 980 | 信息太少，看不出"少在哪" |
| **topic 级统计** | 比条数 + 时间分布 + 字节 | 信息够用，且结论稳定 |

### 裁决：**topic 级统计，不做事件级逐条**

**明确不做**：不对齐"第 i 条 vs 第 i 条"。理由：

1. 存储层不理解 payload 内容，第 i 条之间**没有语义对应关系**
2. 两次录制的时序抖动会让所有配对都错位
3. 即便强行配对，输出也是"N 处不同"而没有可行动的信息

**具体比什么**（每个 topic）：

| 指标 | 说明 |
|---|---|
| `events` | 条数差（绝对值 + 百分比） |
| `bytes` | 字节差 |
| `first_offset_ns` | 首条相对 origin 的时刻（差异说明"这个 topic 晚开始了多久"） |
| `last_offset_ns` | 末条相对时刻 |
| `buckets` | **把相对时间轴等分成 N 桶**（默认 20），比每桶条数 |

### 为什么"分桶"是关键

只有总数时，1000 vs 980 有两种完全不同的情况，看不出来：

```
情况一：整体均匀少 2%     → 可能是采样率变了 → 正常
情况二：后半段突然为 0    → 可能是业务停了 → 严重
```

**分桶对比能区分这两者。** 这是 diff 从"报数字"变成"给线索"的关键。

## 四、★ 裁决 3 · 语义差异（负载变了但条数没变）

### 问题

条数完全相同（都 1000 条），但负载内容变了 —— 这算不算"差异"？

### 裁决：**默认不比 payload**

**理由**：

1. payload 是**任意字节**（存储层"不理解其内容"，见 `docs/11`）
2. 逐字节比会产生大量噪音，且**无法判断"这算不算变化"**
3. 一个字节的差异和整条重写，在"有没有变"这个层面是等价的

### 提供三档选项（默认 `none`）

```
--compare-payload none    （默认）不比
--compare-payload hash    比每条 payload 的哈希，**只报变化条数**，不报"哪里变了"
--compare-payload sample  只比前 100 条哈希（大会话快速判断）
```

**为什么 `hash` 只报条数不报内容**：

> 报"第 3 条 payload 第 17 字节从 0x41 变成 0x42"对排查**毫无帮助** ——
> 人看不出这意味什么。而"这个 topic 有 87/1000 条负载变了"能立刻定位问题范围。

**为什么默认 `none`**：扫全量 payload 很慢。一个跑数天的会话有上千万条记录。
**默认行为必须快**，深度分析由人显式要求。

---

## 五、★★ 核心约束：**不判断「变好还是变坏」**

### 这是整个功能的护栏

```
diff 只报「变了多少」，不报「这样好不好」。
```

**与 `verify` 的「不给业务逻辑下结论」（`docs/14`）是同一条原则。**

### 为什么必须守这条

条数从 1000 变 950，可能是：

| 可能 | 是问题吗 |
|---|---|
| 丢了 50 条（网络/磁盘） | ✗ 是严重问题 |
| 业务量本来就少了 | ✓ 完全正常 |
| 采样率从 100% 调到 95% | ✓ 正常配置变更 |
| 业务提前结束 | ✓ 正常 |

**diff 不知道业务预期，所以它不能判断。**

如果 diff 说"⚠️ 条数下降了 5%，可能丢数据"，
那它就在**猜**，而且猜错的代价比不猜更高 —— 人会去查一个并不存在的问题。
（这与 `prune` 必须留痕、`verify` 不判断业务正确性，是同一个思路。）

### 实现要求

输出里**必须有** `note` 字段：

```json
"note": "这是统计对比，不是逐条 diff；diff 不判断变好还是变坏 —— 条数变化可能来自丢数据，也可能来自业务量变化，请结合上下文判断"
```

**这句不是客套，是契约的一部分。**

## 六、输出契约

### JSON（默认，因为全局 `--format` 默认是 json）

```json
{
  "schema_version": 1,
  "left":  {"session": "...", "events": 1000, "topics": 3, "span_ns": 10000000000},
  "right": {"session": "...", "events": 980,  "topics": 3, "span_ns": 9800000000},
  "alignment": {
    "mode": "relative",
    "left_origin_ns": 1792228100100000000,
    "right_origin_ns": 1792229225900000000,
    "duration_warning": false
  },
  "topics": {
    "added":   [{"topic": "new/topic", "events": 50}],
    "removed": [{"topic": "old/topic", "events": 30}],
    "changed": [{
      "topic": "sensor/temp",
      "left_events": 1000, "right_events": 980,
      "delta": -20, "delta_pct": -2.0,
      "left_first_offset_ns": 0, "right_first_offset_ns": 1200000,
      "buckets": {"n": 20, "left": [...], "right": [...], "max_bucket_delta_pct": 4.5}
    }],
    "same": ["unchanged/topic"]
  },
  "payload_compare": {"mode": "none", "scanned": 0, "changed": 0},
  "business_layer": {
    "dds_events": 0, "dds_topics": 0,
    "probe_events": 2000, "probe_topics": 2
  },
  "note": "这是统计对比，不是逐条 diff；diff 不判断变好还是变坏 ..."
}
```

### `duration_warning` 的判据（把 §二的局限变成可执行的检查）

```c
两侧 span 之比 > 10 或 < 0.1  →  duration_warning = true
```

**并且输出到 stderr 一行警告**：

```
警告: 两侧时长相差 12 倍（10s vs 2min），分桶对比的结论可能被拉伸影响失真
```

**这是"把已知局限变成可检查的信号"** —— 局限写在文档里没人看，
做成 `duration_warning` 字段才会被人看到。

### 退出码

| 码 | 含义 |
|---|---|
| **0** | **无差异**（topic 集合、条数、分桶都一致） |
| 1 | ERROR |
| 2 | USAGE |
| **5** | **PARTIAL**：有差异 |

**「有差异」用 5 而不是 1** —— 差异不是错误。这样脚本能区分：

```bash
stratum diff A B
case $? in
  0) echo "完全一致" ;;
  5) echo "有变化，需人工看" ;;
  *) echo "工具出错" ;;
esac
```

### 文本输出（`--format table`）

```
会话对比
  左: /data/s1   1000 条 / 3 topic / 跨度 10.0s
  右: /data/s2    980 条 / 3 topic / 跨度 9.8s
  对齐: 相对时间（left_origin=1792228100.1, right_origin=1792229225.9）

新增 topic（1）:
  new/topic        50 条

消失 topic（1）:
  old/topic        30 条（左侧有，右侧无）

变化 topic（1）:
  sensor/temp      1000 → 980（-2.0%）
                   首条偏移差 +1.2ms
                   分桶最大偏差 4.5%（第 17 桶）

未变 topic: 2 个

业务层: 探针 2000 条 / 2 topic；业务 0 条 / 0 topic

说明: 这是统计对比，不是逐条 diff；diff 不判断变好还是变坏。
```

## 七、边界与非目标

| 非目标 | 理由 |
|---|---|
| **判断"变好还是变坏"** | diff 不知道业务预期（§五） |
| **事件级逐条 diff** | 时序数据逐条比只产噪音（§三） |
| **默认比 payload** | 性能 + 噪音（§四） |
| **跨机器会话对齐** | 需要时钟同步前提，超出 v1 范围 |
| **自动找"基线会话"** | 需要策略（最近一次？tag 过的？），留给人指定 |
| **合并/修补会话** | 那是 `session merge` 的领域，与 diff 无关 |

**依赖前提**：

* 两个会话都能正常打开（`TimelineImplV2::Open` 成功）
* 两侧时长量级可比（否则 `duration_warning`）

## 八、与现有命令的关系

| 命令 | 关系 |
|---|---|
| `verify` | **复用**业务层两层视角（`IsProbeTopic` / 探针分类）；**不重复**完整性判定 |
| `query` | **复用** `ListTopics` / `FindTopicByName` / `QueryRange` |
| `session list` | 用户靠它找候选会话（diff 不自动选基线） |
| `io` | 无关（对比的是活会话，不是 bundle） |
| `metrics` | 无关（diff 是点对点，metrics 是时间序列） |
| **`diff`（新增）** | 唯一定位：**两份会话的差异** |

## 九、测试计划（一个都不能少）

进 ctest。目标 **57 → ≥62**。

| 用例 | 验证什么 |
|---|---|
| **SelfDiff** | 同一会话与自己比 → 0 差异、退出码 0 |
| **TopicAddRemove** | B 多一个 / 少一个 topic，`added`/`removed` 正确 |
| **CountDelta** | 1000 vs 950，`delta=-50`、`delta_pct=-5.0` 精确 |
| **★ RelativeAlignment** | 两个会话起始时刻不同但内容等价 → **报"基本无差异"**（这是对齐是否正确的关键验证） |
| **PayloadThreeModes** | `none` 不扫（`scanned=0`）/ `hash` 检出变化 / `sample` 只扫 100 |
| **BusinessLayerSplit** | 探针 topic 与业务 topic 分开统计 |
| **EmptySessions** | 两个空会话 / 一空一非空（不能崩） |
| **LargeVolume** | 10 topic × 1000 条 |
| **RandomMultiSeed** | 随机 topic 数/条数 |
| **DurationWarning** | 两侧时长差 10 倍以上 → `duration_warning=true` |
| **BucketsDetectTailLoss** | 构造"后半段为 0"的会话 → 分桶能检出（这是 §三 的关键价值） |

**最后一条最有价值**：它验证 diff 能区分「均匀少 2%」与「后半段停止」——
这正是"报数字"与"给线索"的分界线。

## 十一、实现时发现的一处裁决修正（2026-10-17）

### 问题

裁决 ② 原文写"把相对时间轴等分成 N 桶"，但**没说清这个轴是各自的还是共同的**。

第一版实现用了**各自的 span** 作为分母：

```c
b = (ts - origin) * N / 自己会话的 span      // ← 错
```

于是两个会话都被归一化到 `[0, 1]`，**时长差异被完全抹掉**。

**实测暴露**：构造两个会话，条数都是 100：

```
A：均匀分布，跨度 1s
B：只在前 50% 时间写入 → 跨度因此只有 0.5s
```

用各自 span 归一化后，A 的桶是 `[10,10,...]`、B 的桶也是 `[10,10,...]` ——
**「B 的尾部为空」这个事实消失了**，diff 报告"无差异"。

### 修正

分桶用**两侧 span 的较大者**作为统一参考：

```c
ref_span = max(left.span_ns, right.span_ns)
b = (ts - origin) * N / ref_span            // ← 对
```

于是 A 的 1s 占满 10 桶、B 的 0.5s 只占前 5 桶 —— 尾部为空能被检出。

### 代价（必须同时说明）

两侧时长差很大时，短的那一侧**所有事件都会挤在前几个桶**。

这不是缺陷，是统一参考的必然结果 —— 而且 `duration_warning` 已经会提示"两侧时长差异过大"，
看报告的人知道此时分桶结论要谨慎解读。

**两个信号配合使用**：
```
duration_warning = false  →  分桶对比可信
duration_warning = true   →  分桶可能失真，靠条数/首末偏移判断
```

### 这条修订的意义

它说明「先写裁决、再写实现」这个流程是**有效的** ——
写文档时我就隐约觉得"时间轴"这个说法含糊，但没深究；
实现时被测试逼着必须给出确切答案，才发现含糊的地方正是关键。

**裁决文档不是一次写完就锁定的**，它应该随着实现被修正 ——
但**修正必须回写到文档**，否则下一个读文档的人会重复同样的错误。
