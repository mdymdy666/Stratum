# 已知缺口与限制

> 本文档记录 Stratum 当前**明确未实现或不完整**的能力。
> 目的是避免这些限制被误认为已支持——**沉默的假设比已知的缺陷更危险**。

---

## 1 LSM 引擎

### 1.1 Compaction 不尊重活跃快照 ⚠️

**现状**：`LsmEngine::CompactLocked` 归并 L0 与 L1 时，**不考虑**当前存活的快照。

**后果**：若长期持有某个 `Snapshot`，期间发生 compaction，
该快照应看到的旧版本可能已被合并丢弃 → **快照读到的数据不正确**。

**对比**：参考实现 LSMengine 有 `smallest_snapshot` 机制
（`db/snapshot.h`, `db/version_set.h`），compaction 时会保留
比最老快照更新的所有版本。本引擎尚未实现。

**影响面**：`test_storage_contract` 中的快照测试数据量小、未触发 compaction，
因此**测试通过不代表该场景正确**。

**修复方向**：compaction 时读取 `snapshots_` 中最老的序号，
归并时只丢弃"该序号以下可安全删除"的版本。

### 1.2 `DeleteRange` 需要枚举全部 key

**现状**：范围删除会先收集范围内所有 key，再逐个写 tombstone。

**后果**：对时间轴的"按时间区间淘汰"而言代价高（需遍历该区间的全部数据）。

**修复方向**：引入 **range tombstone**（记录区间而非逐 key 标记），
读取时按区间做可见性判断。这是 LevelDB 本身也没有的特性。

**当前缓解**：保留策略可按"整个 topic 分段"执行，避免细粒度范围删除。

### 1.3 SSTable 无块索引

**现状**：打开 SSTable 时把整个文件载入内存建立有序索引。

**后果**：内存占用与文件大小同量级；单文件数百 MB 可接受，
GB 级以上不合适。

**修复方向**：块级索引 + 延迟加载。这是纯优化，不影响接口。

## 2 时间轴

### 2.1 `seq_in_ts` 计数器未持久化 ⚠️

**背景**：`TimeKey = (topic_id, timestamp_ns, seq_in_ts)`。
`seq_in_ts` 用于区分**同一话题同一时间戳**的多条消息。

**现状**：该计数器存在内存中（`seq_in_ts_state_`），**不随元数据落盘**。

**后果**：时间线关闭后重新打开，计数器从 0 重新开始。
若继续写入**已存在过的时间戳**，新数据的 key 会与历史 key 冲突，
**旧数据被静默覆盖**。

**触发条件**：跨进程重启 + 写入重复时间戳。正常连续录制不会遇到。

**为什么没修**：需要把每个话题的计数器纳入元数据（`meta_codec`），
涉及格式版本升级。当前 `kCurrentFormatVersion = 1`，
增加字段应升为 2 并保留向后兼容读取。

**临时规避**：重开后避免写入历史时间戳区间。

### 2.2 `GetStateAt` 使用正向扫描

**现状**：查询"某时刻状态"时会正向扫描到目标时刻并取最后一条。

**代价**：5 万条数据下平均延迟 **1034 μs**（见性能报告）。

**原因**：开发中选择"正确性优先"——反向迭代（`SeekToLast`）曾出现
定位不准的问题，因此改用只依赖 `Next()` 的实现。

**修复方向**：见 `06-performance-report.md` 第 3.3 节。

## 3 录制 / 回放

### 3.1 回放需把整个范围载入内存

**现状**：`Player::Play` 先收集范围内**全部**事件到 `std::vector`，
按时间戳排序后再逐条发送。

**后果**：回放超大范围（如数小时数据）会占用大量内存。

**修复方向**：改为真正的多路归并迭代器（逐话题有序读取 + 归并）。
当前实现优先保证**全局时序正确**。

### 3.2 回放速率控制精度未验证

**现状**：速率控制基于 `steady_clock` 的绝对目标时刻计算，不累积漂移。

**未验证**：实际时间精度（回放 1 分钟数据的累计偏差）未测量。
测试中统一使用 `rate = 0`（尽可能快）以缩短测试时间。

**待办**：补充回放时序精度测试。

### 3.3 未实现 DDS 协议层

**现状**：`IDdsBackend` 是接口，当前只有 `MockBackend`（测试用）。
**自研 RTPS 实现尚未开始**。

**后果**：Stratum 目前**无法真正从 DDS 网络录制数据**，
端到端能力仅在模拟后端上验证。

**这是最大缺口**。原设计要求"RTPS 线格式兼容"，
需要实现：消息编解码、SPDP/SEDP 发现、UDP/SHM 传输。

## 4 测试

### 4.1 已覆盖

| 类型 | 用例数 | 说明 |
|---|---|---|
| 单元 | 10 | TimeKey 编解码 |
| 集成 | 16 | Timeline 语义 + 端到端录放 |
| 契约 | 4 | 存储引擎（双后端） |
| 随机 | 5 | 固定种子，可复现 |
| 压力 | 4 | 含吞吐下界断言 |
| 真实形态 | 6 | 抖动/丢帧/漂移/突发 |

**合计 45 个用例**，7 个测试套件全部通过。

### 4.2 缺口

| 项 | 说明 |
|---|---|
| **多线程写入** | 未测试并发写（当前实现串行化写入） |
| **长时间运行** | 未做小时级持续录制测试 |
| **故障注入** | 未测试磁盘满、WAL 损坏、进程被 kill |
| **跨平台** | 仅在 Linux 验证（代码使用 POSIX API，不支持 Windows） |
| **协议一致性** | 无 RTPS 实现，故无互操作测试 |
| **内存泄漏** | 仅对端到端测试跑过 ASan，未全量覆盖 |

### 4.3 ASan 使用建议

项目已内置开关：

```bash
cmake -S . -B build-asan -G Ninja -DCMAKE_BUILD_TYPE=Debug \
      -DSTRATUM_ENABLE_SANITIZERS=ON
```

**强烈建议**：提交前对所有测试跑一次 ASan。
开发中正是靠它定位了一个测试脚手架的 use-after-free。

## 5 代码审查

**已完成 0 次系统性代码审查**（要求 ≥3 次）。

当前的代码质量保障手段是：
1. `-Wall -Wextra -Wpedantic` 零警告
2. 45 个测试用例覆盖
3. ASan 验证（部分）
4. 关键设计决策均有注释说明理由

**尚未做**：从第三方视角审查架构合理性、接口设计、错误处理完备性。

## 6 优先级建议

| 优先级 | 项 | 理由 |
|---|---|---|
| P0 | RTPS 协议层 | 否则产品无法使用 |
| P0 | Compaction 快照保护 | 当前是**静默错误**，最危险 |
| P1 | 代码审查 3 轮 | 明确要求，且能发现上述之外的隐患 |
| P1 | `seq_in_ts` 持久化 | 跨重启的静默数据覆盖 |
| P2 | `GetStateAt` 性能 | 有量化数据，优化方向明确 |
| P2 | 故障注入测试 | 提升可信度 |
| P3 | SSTable 块索引 | 规模瓶颈尚未触及 |
| P3 | range tombstone | 保留策略可绕开 |
