# Stratum 性能报告

> 采集环境：WSL2 Ubuntu / GCC 13.3.0 / `-O2 -g` (RelWithDebInfo) / 单线程写入
> 采集工具：`build/benchmarks/stratum_bench`
> 复现命令：`cd build && ./benchmarks/stratum_bench`

---

## 1 核心数据

### 1.1 存储引擎写入吞吐（20 万条，负载 27 字节）

| 引擎 | 耗时 | 吞吐 |
|---|---|---|
| MemoryEngine | 0.058 s | **3,448,460 ops/s** |
| LsmEngine（WAL + MemTable） | 0.402 s | **497,027 ops/s** |

**LSM 相对内存引擎慢约 7 倍**，这是正常的：LSM 每条都要写 WAL（顺序追加），
而内存引擎只操作 `std::map`。

### 1.2 LSM 生命周期开销

| 操作 | 耗时 |
|---|---|
| 关闭（含内存表刷盘） | 0.169 s |
| 重新打开（含 WAL 重放 + SSTable 载入） | 0.081 s |

20 万条数据的恢复仅 81 ms，**启动恢复不是瓶颈**。

### 1.3 时间轴范围扫描

| 操作 | 数据量 | 耗时 | 吞吐 |
|---|---|---|---|
| 全量扫描 | 100,000 条 | 0.007 s | **14,133,085 条/s** |

扫描吞吐达 1400 万条/秒，得益于底层 `std::map` 的有序遍历与内存局部性。

### 1.4 追加吞吐 vs 负载大小

| 负载大小 | 条/秒 | 带宽 |
|---|---|---|
| 16 B | 4,286,061 | 65.4 MB/s |
| 64 B | 4,362,522 | 266.3 MB/s |
| 256 B | 4,321,075 | 1,055.0 MB/s |
| 1 KB | 1,509,517 | 1,474.1 MB/s |
| 4 KB | 370,819 | 1,448.5 MB/s |

**规律**：
- 16 B ~ 256 B 区间，**条数吞吐几乎不变**（约 430 万条/秒），
  说明小负载下开销由**固定成本**（key 编码、map 插入）主导，而非数据拷贝。
- 1 KB 起吞吐开始下降，4 KB 时降至 37 万条/秒，
  带宽稳定在约 1.45 GB/s —— 此时**内存带宽成为瓶颈**。

**工程含义**：传感器数据典型负载（16~256 字节）恰好在最优区间。

### 1.5 定点查询（`GetStateAt`）

| 指标 | 值 |
|---|---|
| 查询次数 | 2,000 |
| 吞吐 | 967 次/s |
| **平均延迟** | **1034 μs** |

⚠️ **这是当前最明显的性能短板**，见第 3 节分析。

## 2 本轮修复的性能缺陷

### 2.1 LSM 每条写入都 fsync（严重）

**现象**：压力测试中 5 万条写入耗时 **66.7 秒**（约 750 ops/s）。

**根因**：`LsmEngine::PutBatch` 中：

```cpp
const bool sync = (options.sync == kAlways) || (options.sync == kBatch);
```

`WriteOptions::sync` 的**默认值是 `kBatch`**，于是默认配置下每条写入都调用
`fsync`。而 `kBatch` 的语义本应是"由引擎决定批量提交时机"，不是"每条都落盘"。

**修复**：只有 `kAlways` 才逐条 fsync；`kBatch` 改为在 `Flush()` / `Close()`
时显式 `WAL::Sync()`。

**效果**：

| 场景 | 修复前 | 修复后 | 提升 |
|---|---|---|---|
| 5 万条 LSM 写入 | 66.72 s | **1.02 s** | **65×** |
| 存储契约测试 | 1.58 s | **0.05 s** | **31×** |
| 20 万条写入吞吐 | ~750 ops/s | **497,027 ops/s** | **约 660×** |

**教训**：枚举值的**语义**必须在实现中严格兑现。`kBatch` 被实现成
`kAlways` 是"看起来无害"的错误，但它让默认配置下的性能差了两个数量级——
而这类问题**只有压力测试能发现**（功能测试全部通过）。

### 2.2 时间戳乱序导致静默丢数据（正确性，见缺陷报告）

`NextSeqInTsLocked` 早期实现"时间戳变化则重置序号为 0"，
在时间戳乱序（`A, A, B, A`）时第 4 条会与第 1 条 key 冲突并覆盖。
修复后改为每 topic 内单调递增。详见 `design/05-known-gaps.md`。

## 3 已知性能短板：定点查询

### 3.1 现状

`GetStateAt` 平均延迟 **1034 μs**（约 1 ms），随数据量线性增长。

### 3.2 原因

实现采用**正向扫描取最后一条**：

```cpp
for (; it->Valid(); it->Next()) { last = ...; }   // 扫描 [begin, as_of_ns] 全部数据
```

这是我在开发中的**有意取舍**：当时反向迭代（`SeekToLast`）存在正确性问题，
我选择"正确性优先"，用扫描保证结果准确，并在代码注释中记录了优化方向。

现在有了量化数据，可以确认这个取舍的代价。

### 3.3 优化方向（按代价排序）

| 方案 | 预期收益 | 代价 |
|---|---|---|
| **反向迭代**（修复 `SeekToLast` 语义） | 1 ms → 微秒级 | 需验证 LSM 反向迭代正确性 |
| **二分定位**：利用 SSTable 的有序性直接跳到 `as_of_ns` | 同上 | 需 SSTable 支持按 key 定位 |
| **保留点索引**：为 RetentionPoint 建索引，避免全扫 | 高频查询场景收益大 | 增加写路径开销 |
| **上层缓存**：对"最近状态"缓存（时间轴场景查询常集中在近期） | 实际收益最大 | 需处理失效 |

**建议优先级**：先做**反向迭代**（收益/代价比最高），
再做**上层缓存**（贴合真实查询模式）。

## 4 性能特征总结

### 4.1 适合的场景

| 场景 | 依据 |
|---|---|
| 高频传感器数据录制（16~256 B） | 430 万条/秒、1 GB/s 级带宽 |
| 大范围数据回放/导出 | 1400 万条/秒扫描 |
| 快速启动恢复 | 20 万条 81 ms |
| 按时间范围查询 | 扫描吞吐高 |

### 4.2 需要改进的场景

| 场景 | 现状 | 改进方向 |
|---|---|---|
| 高频定点查询（>1 万次/秒） | 1 ms 延迟，仅 967 次/秒 | 见 3.3 节 |
| 超大范围全量扫描 | 结果集全部载入内存 | 改多路归并迭代器 |

### 4.3 未做的性能工作

- **多线程写入**：当前写入路径持单锁，未验证并发写扩展性
- **并发读**：压力测试验证了正确性，但未测吞吐
- **Compaction 影响**：未测 compaction 期间的读写延迟抖动
- **长时间稳定性**：未做小时级持续写入测试

## 6 诚实声明

1. 以上数据为**单次测量**，未做多次取平均，也未统计方差。
   生产决策前应重复测量。
2. 采集环境为 **WSL2**（虚拟化层会引入开销），
   裸机 Linux 上的绝对性能预计更好。
3. 测试数据由程序生成，**不代表**特定真实业务的负载分布。
4. 定点查询的 1 ms 延迟是在 **5 万条数据**下测得的，
   数据量增长时该延迟会线性上升。
