# 测试数据量标准（长期生效）

## 规则

**测试默认使用大数据量，不使用"刚好能通过"的小数据。**

## 为什么定这条规则

第 1 轮代码审查的结论：

> 45 个测试用例全绿，是因为它们集中在「**单进程、单次打开、数据量小到不触发
> compaction**」的甜区；9 个 Critical/High 里有 **7 个**是在测试未覆盖的路径上
> 实测复现的。

具体例子：

| 缺陷 | 为什么小数据量测不出 |
|---|---|
| Compaction 不删旧文件 | 数据量小 → 从不触发 compaction |
| sequence 水位丢失 | 只写一次 → 重启后不写同一 key |
| LSM 迭代器快照语义错误 | 数据量小 → 不经过 SSTable 路径 |
| Recorder 队列记账错误 | 发送量小 → 队列从未接近上限 |

**共同点**：小数据量让代码走"最顺的那条路径"，绕过了所有错误处理、
分层、合并、溢出分支。

## 具体标准

| 测试类型 | 数据量标准 | 必须触发的路径 |
|---|---|---|
| 单元测试 | ≥ 10,000 条 | — |
| 存储引擎测试 | ≥ 50,000 条 或 ≥ 4 MB | **至少 2 次 compaction** |
| 端到端测试 | ≥ 20,000 条 | compaction + 重启恢复 |
| 压力测试 | ≥ 100,000 条 | 多次 flush + compaction |
| 队列/缓冲测试 | 必须**超过**上限 | 溢出策略分支 |
| 持久化测试 | 必须**重启后再写** | sequence 水位恢复 |

### 强制要求

1. **凡涉及 LSM 的测试，必须显式把 `flush_threshold` 调小**
   （如 `SetMemTableFlushThreshold(16 * 1024)`），
   确保即使数据量不大也**必然触发多次 compaction**。

2. **凡涉及持久化的测试，必须包含"重启后再写入"步骤**。
   只写一次然后读回，无法验证水位/元数据恢复。

3. **凡涉及队列/缓冲的测试，发送量必须超过配置上限**，
   否则溢出分支永远不被执行。

4. **新增配置项时，必须配一条"设置后行为确实改变"的断言**。
   未生效的配置项是最难发现的问题类别（第 4 轮审查发现 5 个）。

## 反例（不要这样写）

```cpp
// 反例：数据量小，永远不触发 compaction，测不出任何分层缺陷
for (int i = 0; i < 100; ++i) { engine->Put(...); }
CHECK_EQ(engine->Get(...), expected);
```

## 正例

```cpp
// 正例：小阈值强制多次 compaction + 重启后再写 + 断言资源有界
engine->SetMemTableFlushThreshold(16 * 1024);
for (int i = 0; i < 50000; ++i) { engine->Put(...); }
CHECK_LE(CountSstFiles(dir), 8);          // 资源断言
engine->Close();

engine->Open(dir);                         // 重启
engine->Put(same_key, newer_value);        // 重启后再写同一 key
engine->CompactRange("", "");
CHECK_EQ(engine->Get(same_key), newer_value);  // 新值必须胜出
```

## 教训

**测试的价值不在于"通过"，而在于"能在多大范围内失败"。**
数据量是决定这个范围的主要因素之一。
